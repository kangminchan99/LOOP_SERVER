# 게시글 목록 단계별 부하 테스트

전체 학습 순서는 [실서비스 운영 로드맵](production-operations-roadmap.md)을 먼저 참고한다. 이 문서는 그중 읽기 부하 실험의 실행 지침이며, 운영 계측이나 동시 작성 정합성 구현을 대신하지 않는다.

## 1. 목적과 현재 상태

현재 데이터 그대로 `GET /posts?limit=20`에 동시 요청을 늘려, 트래픽이 몰릴 때 처리량이 정체되거나 응답 지연·오류가 증가하는지 확인한다.

이번 작업은 **테스트 계획 문서화**다. 테스트 결과나 성능 개선을 완료했다는 의미가 아니다. 서버 코드, 요청 제한, DB 데이터는 변경하지 않는다.

- 테스트 종류: 단일 읽기 API의 단계별 동시 연결 부하 테스트. 자원과 응답 지표를 함께 관찰하는 병목 탐색이다.
- 기대 효과: 현재 환경의 기준 성능 확보, 성능이 꺾이는 구간 식별, 개선 우선순위 선정, 개선 전후 비교 근거 확보.
- 한계: 테스트 자체가 성능을 개선하지 않는다. 유명 서비스의 실제 사용자 수나 운영 수용량을 증명하는 테스트도 아니다.
- 이번 범위 밖: 대량 데이터 추가, 쓰기 API, FCM·AI 호출, 장애 주입, 장시간 안정성, WebSocket·SSE, Flutter 렌더링 성능.

## 2. 프로젝트에서 확인한 전제

2026-09-18 코드 기준이며 실제 실행 직전에 다시 확인한다.

| 확인 위치 | 현재 동작 | 측정에 미치는 영향 |
| --- | --- | --- |
| `src/app.module.ts` | 전역 ThrottlerGuard, 기본 60초당 100회 | 같은 IP에서 보내는 목록 요청이 제한될 수 있음 |
| `src/posts/controllers/posts/posts.controller.ts` | 목록 조회는 전역 제한 적용, 검색은 별도 60초당 60회 | 제한에 걸린 결과를 API 처리 한계로 해석하면 안 됨 |
| `src/posts/services/posts/posts.service.ts` | limit·cursor별 Redis 목록 캐시, TTL 10초 | 같은 첫 페이지 반복은 캐시 적중 경로 중심이며 만료 구간도 섞임 |
| `package.json` | `start:dev`는 watch, `start:prod`는 production 환경 | 실행 방식·환경이 바뀌면 직접 비교 불가 |
| `src/app.module.ts` | 환경에 따라 DB 동기화·SSL 동작 변경 | 단순히 prod 명령으로 바꾸면 다른 DB나 연결 설정을 사용할 위험 |
| `src/database/seeds/seed-large-data.ts` | 개발 DB에 seed 생성, 패턴에 맞는 기존 seed 삭제 | 이번 테스트 준비를 위해 실행하지 않음 |

로컬의 `127.0.0.1`로 요청해도 NestJS가 연결하는 DB·Redis는 원격일 수 있다. 실제 연결 대상 확인이 먼저다. 비밀번호·토큰·환경변수 원문은 결과 문서에 남기지 않는다.

## 3. 실행 전 안전 조건

- 본인 소유의 격리된 로컬/테스트 서버만 대상으로 한다. 운영·공유 서버에는 별도 승인 없이 실행하지 않는다.
- 기존 데이터는 변경하지 않는다. seed, 캐시 전체 삭제, Redis `FLUSHALL`, DB 삭제는 하지 않는다.
- 서버와 DB·Redis 연결 대상, 서버 포트, 현재 데이터 건수를 확인한다.
- 이미 떠 있는 서버를 무작정 종료하거나 중복 실행하지 않는다.
- 자동 작업/큐 워커 등 동시에 실행되는 작업을 기록한다. 외부 유료·메시지 발송 작업이 개입하는 환경은 먼저 분리한다.
- CPU·메모리 관찰 수단을 먼저 준비하고, 응답 불능·연속 오류·과도한 메모리 압박이 보이면 부하를 중단한다.
- 요청 제한을 제외한 성능 측정은 외부에 노출되지 않은 테스트 환경에서만 수행한다. 운영 제한을 제거하거나 가짜 전달 IP 헤더로 우회하지 않는다.

## 4. 요청 제한 검증과 처리 성능 측정 분리

### A. 요청 제한 정책 검증

현재 제한을 유지한 상태에서 정상 요청과 제한 초과 시 429를 확인한다. 이 결과는 **보호 정책 검증**이지 최대 처리량 측정이 아니다. 이미 제한이 동작하는 것을 확인했다면 반복 고부하 검증은 불필요하다.

### B. 병목 측정

테스트 전용 서버에서 대상 API의 제한을 명시적으로 조정/제외하고 변경 내용을 기록해야 한다. 아직 이 구성이 구현된 것은 아니다. 격리·설정을 확인하기 전에는 아래 단계별 부하 명령을 실행하지 않는다.

요청 제한에서 반환한 빠른 429가 많으면 Req/Sec가 높고 지연이 낮아 보여도 정상 처리 성능은 낮을 수 있다. 401·403·404·500 역시 성공으로 세지 않는다.

## 5. 실행 순서

### 5-1. 측정 환경 고정

아래 항목을 기록하고 모든 비교 테스트에서 유지한다.

- Git 커밋과 미커밋 변경 여부, Node·autocannon 버전.
- 서버 실행 명령과 환경 모드. watch 없는 빌드 실행이 비교에 적합하지만, DB·SSL 등 환경이 바뀌지 않도록 별도 확인 후 결정한다.
- 테스트 장비 CPU·메모리, Docker 자원 제한, 서버/DB/Redis/부하 도구의 배치.
- 사용자·게시글·댓글 건수, 인덱스, DB pool 크기, 캐시 TTL, 요청 제한 적용 여부.
- URL, 연결 수, 시간, 타임아웃, 워밍업 조건, 반복 횟수.

서버와 부하 도구가 같은 컴퓨터에 있으면 CPU·메모리·디스크를 경쟁한다. 로컬 결과를 운영 처리량으로 환산하지 않는다.

### 5-2. 단일 요청 확인

```bash
curl -i --max-time 10 "http://127.0.0.1:3000/posts?limit=20"
```

- HTTP 200인지, 응답 JSON이 현재 DTO와 일치하는지 확인한다.
- 기존 데이터가 충분하다면 실제 목록이 내려오는지, limit이 반영되는지 확인한다. 빈 목록만 반환하는 경우도 기록한다.
- `ECONNREFUSED`: 서버 실행·포트부터 확인한다. 성능 병목 결과가 아니다.
- 429: 제한 해제 시점/정책을 확인한다. 즉시 부하 수준을 늘리지 않는다.
- DB 연결 실패·500·비정상 응답이면 원인 해결 후 다시 시작한다.

### 5-3. 워밍업

테스트 전용 제한 구성이 완료된 뒤, 각 측정 전에 같은 조건으로 실행한다. 이 결과는 본 측정에 포함하지 않는다.

```bash
npx autocannon -c 1 -d 5 "http://127.0.0.1:3000/posts?limit=20"
```

처음 실행하는 npx는 패키지 설치를 요청할 수 있다. 도구를 먼저 준비하고 사용 버전을 기록/고정한다. 워밍업 이후에도 캐시는 10초마다 만료되므로 모든 요청이 캐시 적중이라고 가정하지 않는다.

### 5-4. 동시 연결을 단계별로 증가

각 명령을 **순서대로 하나씩** 실행한다. 앞 단계 결과를 확인하고 안정적일 때만 다음 단계로 넘어간다.

```bash
npx autocannon -c 1 -d 30 -l "http://127.0.0.1:3000/posts?limit=20"
```

```bash
npx autocannon -c 10 -d 30 -l "http://127.0.0.1:3000/posts?limit=20"
```

```bash
npx autocannon -c 50 -d 30 -l "http://127.0.0.1:3000/posts?limit=20"
```

```bash
npx autocannon -c 100 -d 30 -l "http://127.0.0.1:3000/posts?limit=20"
```

`-c`는 동시 연결 수, `-d`는 초 단위 실행 시간, `-l`은 상세 지연 분포 출력이다. 동시 연결 수는 실제 사용자 수가 아니다. 출력되는 percentile을 사용하고, 해당 도구 버전이 p95를 출력하지 않으면 인접 percentile을 p95로 바꿔 적지 않는다. 옵션은 [autocannon 공식 문서](https://github.com/mcollina/autocannon#usage)를 따른다.

각 단계 사이 CPU·메모리·연결 상태가 안정될 때까지 쉬고, 최소 3회씩 같은 조건으로 반복한다. 30초는 초기 탐색용이며 장시간 안정성 검증을 대체하지 않는다.

## 6. 무엇을 관찰할 것인가

| 지표 | 의미 | 검증 방법 |
| --- | --- | --- |
| 정상 응답 처리량 | 초당 정상 200 응답 수 | 도구 전체 출력과 상태 코드별 집계 확인. 총 Req/Sec와 구분 |
| p50·p99 지연 | 일반적인 요청과 느린 꼬리 구간의 지연 | 동일 옵션으로 반복 비교. 평균만 보지 않음 |
| HTTP 오류 | 429·5xx 등 정상 처리되지 않은 응답 | non-2xx 개수 및 서버 로그의 코드별 내역 확인 |
| 연결 오류·Timeout | 완료하지 못한 요청 | HTTP 오류와 별도 기록. 도구의 errors에 timeout이 포함되면 중복 합산하지 않음 |
| 서버 CPU·메모리 | 연산 포화·메모리 압박 가능성 | 활동 모니터/프로세스 관찰을 같은 시간대에 기록 |
| DB·Redis 자원 | 저장소 측 포화 가능성 | 컨테이너 CPU·메모리 및 DB 대기 상태 확인 |
| DB 쿼리·연결 대기 | 쿼리가 느린지, 연결을 기다리는지 | 필요 시 pg_stat_activity, 실행 계획, pool 대기 계측 추가 |
| 부하 도구 자원 | 요청 생성 자체가 한계인지 | 부하 프로세스 CPU와 서버 자원을 함께 관찰 |

컨테이너 자원은 별도 터미널의 `docker stats`로 관찰할 수 있다. NestJS를 호스트에서 실행했다면 해당 프로세스는 docker stats에 나오지 않는다. DB pool 대기, 캐시 적중률, 이벤트 루프 지연은 현재 자동으로 측정된다고 가정하지 않으며 필요 시 다음 작업에서 계측한다.

## 8. 병목 판단과 개선 검증

### 병목 의심 신호

- 동시 연결 증가에 비해 정상 처리량이 늘지 않고 p99가 지속적으로 증가한다.
- 응답 시간이 길어지면서 오류·Timeout이 발생한다.
- 같은 시간대에 서버 CPU 포화, DB 대기, 메모리 압박 등이 함께 관찰된다.

이는 병목 **후보**다. DB, Redis, NestJS, 로그 출력, 네트워크, 부하 도구 중 어디가 원인인지는 추가 관찰로 구분한다. CPU가 낮아도 I/O·연결 대기로 느릴 수 있다.

### 유효한 테스트의 조건

- 기대한 응답 본문과 상태 코드가 맞고, 제한 응답 위주의 결과가 아니다.
- 환경·데이터·캐시·실행 방식이 동일하며 반복 결과가 함께 제시된다.
- HTTP 오류와 연결 실패를 누락하지 않는다.
- 첫 실행에는 보편적인 합격 지연 수치를 임의로 지정하지 않는다. 우선 기준선을 확보하고 서비스 목표(p99·정상 처리량·허용 오류율)를 정한다.

### 개선 전후 비교

1. 관찰 지표로 원인 가설을 한 가지 선정한다.
2. 필요한 계측이나 쿼리 실행 계획으로 가설을 확인한다.
3. 한 번에 한 가지 변경만 적용한다. 근거 없이 pool·캐시·인덱스를 동시에 바꾸지 않는다.
4. 같은 데이터·부하 조건으로 3회 이상 재측정한다.
5. 정상 처리량, p99, 오류, 자원 사용량을 모두 비교한다. 가장 빠른 한 번만 선택하거나 percentile을 단순 평균해 통합 p99로 부르지 않는다.
6. 결과에 따라 다음 변경을 결정한다. 제한 변경으로 429만 줄어든 것을 DB 최적화로 기록하지 않는다.

## 9. 이번 결과로 알 수 없는 것과 다음 단계

같은 첫 페이지를 반복하는 테스트만으로 전체 서비스의 동시 사용자 수, 검색/쓰기 성능, 데이터 정합성, 운영 HTTPS·프록시 경로의 성능은 알 수 없다. 고정 연결 방식은 서버가 느려지면 다음 요청 발생도 늦어지므로, 외부에서 일정 속도로 계속 유입되는 트래픽과도 다르다.

기준선을 확보한 다음에는 아래 순서로 확장한다.

1. 캐시 적중·만료 구간 및 DB 대기를 계측한다.
2. 실제 존재하는 cursor·게시글 ID로 분산 조회 시나리오를 만든다. 캐시 우회를 위해 무의미한 랜덤 쿼리를 붙이지 않는다.
3. 격리된 환경에서 목록 → 상세 → 댓글 작성 행동을 섞고 외부 호출을 차단한다.
4. 일정 요청 유입률, 순간 폭증, 긴 시간의 안정성을 각각 테스트한다.
5. 필요할 때 데이터 규모를 늘리고, 다시 같은 비교 과정을 반복한다.

현재 다음 작업은 **연결 대상과 단일 응답 확인 후, 테스트 전용 요청 제한 정책을 설계하는 것**이다. 문서 작성만으로 이 선행 조건이 완료되지는 않는다.
