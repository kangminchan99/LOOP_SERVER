# 로컬 게시글 읽기 부하 진단 결과

## 조건

- Node 24.21.0, 빌드된 Nest 서버, 로컬 PostgreSQL·Redis.
- 같은 Mac에서 서버와 autocannon 실행, GET `/posts?limit=20`.
- 동시 연결 100개, 각 30초. 모든 측정 200 응답, 오류·타임아웃 0.
- 개발 부하 테스트 모드로 Throttler만 우회. 운영 수용량/사용자 수로 환산 불가.
- Redis TTL을 매초 관찰하고 100ms 초과 응답의 시점을 기록.

## 측정

| 조건 | 평균 req/s | p99(ms) | 최대(ms) | 가장 낮은 1초 req/s |
| --- | ---: | ---: | ---: | ---: |
| 수정 전 TTL 10초 | 13,243 | 10 | 1,300 | 95 |
| 수정 전 TTL만 임시 120초 | 14,378 | 10 | 72 | 12,493 |
| 수정 전 TTL 10초 재측정 | 12,407 | 12 | 1,570 | 108 |
| LIMIT 수정 후 TTL 10초 | 14,080 | 12 | 256 | 10,597 |
| LIMIT 수정 후 TTL 10초 재측정 | 15,285 | 9 | 43 | 13,793 |

수정 후 첫 측정 초반에는 린트·타입 검사 작업이 일부 겹쳤으므로 정확한 처리량 비교에는 재측정 결과를 우선 참고한다.
수정 후 첫 측정의 100ms 초과 응답은 시작 구간에만 발생했다.
단일 장비·짧은 반복 실험이므로 수치를 보장 성능이나 확정적인 개선율로 사용하지 않는다.

## 확인한 원인

기존 `innerJoin(User, ...) + take(limit + 1) + getRawMany()` 조합에서
설치된 TypeORM이 생성한 SQL에 `LIMIT`이 없었다.
캐시 미적중 시 필요한 21행보다 많은 데이터를 조회/전송/변환한 뒤 JavaScript에서 20개로 잘랐다.
수정 전 긴 지연은 약 10~11초와 22~23초의 캐시 만료·재충전 구간과 겹쳤다.
TTL을 120초로 늘려 만료를 제외했을 때 해당 지연이 사라졌고,
SQL LIMIT 적용 후에는 TTL 10초로도 같은 장시간 지연이 재현되지 않았다.

이는 이번 스파이크의 주요 원인을 뒷받침하지만 모든 병목이 해결됐다는 의미는 아니다.
CPU, GC, DB 대기별 기여율과 캐시 미적중 시 중복 쿼리 수까지 정량 분해하지는 않았다.

## 유지/복구

- 목록 및 동일 raw 조회 방식의 검색에서 `.take(limit + 1)`을 `.limit(limit + 1)`로 수정 유지.
- 이 JOIN은 작성자 PK로 연결하는 다대일 관계여서 게시글 행 수를 늘리지 않는다.
  일대다 JOIN의 엔티티 페이지네이션에 동일 수정을 무조건 적용하면 안 된다.
- Redis TTL은 원래 10초로 복구. 서비스 코드 TTL 자체는 변경하지 않았다.
- 페이지네이션 응답뿐 아니라 실제 SQL LIMIT과 raw 반환 행 수를 검사하는 통합 테스트 추가.
- 테스트 전용 스키마 외 개발 DB 데이터의 작성/삭제는 하지 않았다.
- 부하 테스트 종료 후 `LOAD_TEST_MODE=false`로 복구하고 서버를 재시작한다.
