# Loop 실서비스 운영 학습 로드맵

작성: 2026-09-21. 상태: 계획 수립. 이번 변경은 문서만 작성하며 패키지 설치·앱/서버 코드 변경·부하 실행·인프라 배포는 하지 않았다.

## 1. 무엇을 배우는가

목표는 많은 사용자가 쓰는 앱에서 문제를 감지하고, 원인을 좁히고, 데이터 유실 없이 복구하며, 안전하게 변경을 배포하는 능력이다. 다운로드 수 자체는 동시 사용자 수나 필요한 서버 대수가 아니다. 실제 활성 사용자, 요청률, 연결 수, 데이터 증가량, 허용 지연과 실패율로 운영 목표를 정한다.

첫 프로젝트는 **인기 게시글에 트래픽이 집중됐을 때 운영 지표로 병목을 찾고 개선하는 것**이다. 최대 RPS만 기록하지 않고 오류·응답 정확성·느린 요청·회복까지 확인한다. 최종적으로 동시 작성, 장애 복구, 구버전 앱 공존까지 확장한다.

### 기존 문서와의 관계

- 이 문서: 전체 학습 순서와 첫 운영 계측 구현 계획.
- [게시글 목록 부하 테스트](posts-load-test.md): 읽기 API의 단계별 부하 실행·결과 기록 절차.
- [server.md](../server.md): 프로젝트 기능별 작업 안내와 이 로드맵의 진입점.
- Flutter 저장소의 `docs/APP_PERFORMANCE_GUIDE.md`: 앱 프레임·페이지 이동·통신·동시성 종합 가이드. 서버 지표가 앱 프레임을 대신하지 않는다.

사용자는 한 단계씩 직접 구현한다. 다음 단계 전에 현재 파일과 검증 결과를 확인한다. 코드 대신 문서만 요청한 단계에서는 구현이나 패키지 설치를 진행하지 않는다.

## 2. 전체 단계와 완료 조건

| 단계 | 배울 기술 | 실습 | 완료 증거 |
| --- | --- | --- | --- |
| A. 관측 기반 | 메트릭·대시보드·경보 | 요청량, 지연, 오류, 자원 사용 수집 | 정상/실패 요청이 지표에 반영되고 경보 발동·해제 확인 |
| B. 읽기 부하 대응 | 캐시·쿼리·pool·용량 분석 | 인기 글 상세·댓글에 집중 요청 | 부하별 p99·정상 처리량·DB 대기와 원인 가설 |
| C. 동시 작성 정합성 | 멱등성·트랜잭션·제약 | 중복 제출, 응답 유실 후 재시도 | DB 중복/유실 없고 결과 불명 요청의 최종 상태 확인 |
| D. 비동기 처리 복구 | 큐·outbox·재처리 | 저장 후 큐 실패, 워커 재시작 | 후속 작업 복구 및 중복 부작용 억제 증거 |
| E. 데이터 운영 | 마이그레이션·백업·복원 | 테스트 DB 복구, 신구 스키마 전환 | 복원 시간·허용 데이터 손실 범위 확인 |
| F. 안전한 릴리스 | CI/CD·기능 플래그·점진 배포 | 특정 기능 중단·롤백·구버전 앱 호출 | 구버전 호환성, 단계별 배포/중단 절차 |
| G. 장애 대응·용량 계획 | SLO·런북·회고·비용 | 과부하/의존 서비스 장애 훈련 | 탐지·복구 시간, 재발 방지, 필요한 확장 근거 |

보안은 마지막에만 추가하지 않는다. 모든 단계에서 인증·인가·내부 관리 엔드포인트 보호·개인정보 최소 수집을 유지한다. Kubernetes·샤딩·대규모 클러스터는 측정 근거가 생겼을 때 검토한다.

## 3. 이번에 시작하는 구조

```text
Flutter 앱 / 테스트 부하 도구
             ↓ HTTP
NestJS → PostgreSQL / Redis / BullMQ
  └─ 메트릭 Registry → 내부 /metrics ← Prometheus 주기 수집
                                            ↓
                                         Grafana
```

- Node 메트릭 클라이언트: NestJS 프로세스 안에서 요청 수·시간 등을 기록한다.
- Prometheus: 기록된 지표를 주기적으로 읽어 시계열로 저장한다.
- Grafana: 저장된 지표를 그래프로 비교한다. 그 자체가 HTTP 계측을 수행하지는 않는다.
- OpenTelemetry: 이후 개별 요청의 HTTP→DB→큐 구간 추적을 추가할 때 검토한다. 처음부터 같은 지표를 두 도구로 중복 수집하지 않는다.

기존 관리자 SSE 상태 표시는 운영 추이 저장·집계·경보를 대신하지 않는다. 앱에 Prometheus를 직접 연결하거나 공개하지 않는다.

## 4. A단계: 구현을 한 번에 하나씩

### A-1. Node 실행 환경 정렬 준비 — 현재 시작 단계

2026-09-21 확인 결과:

| 위치 | 현재 값 |
| --- | --- |
| 이 작업의 터미널 `node --version` | v20.12.1, nvm 경로 사용 |
| `.github/workflows/server-ci.yml` | Node 24 |
| `Dockerfile` builder / production | 둘 다 node:20-alpine |
| 프로젝트 `.nvmrc` | 없음 |

Node 24 LTS를 목표로 맞춘다. Node 20은 공식 지원 종료 상태다. 최신성은 가장 큰 버전 번호를 고르는 것이 아니라 지원 기간·패키지 호환성·배포 재현성을 확인하는 것이다. [Node 공식 릴리스 상태](https://nodejs.org/en/about/previous-releases)

서버 디렉터리의 사용자 터미널에서 순서대로 실행한다.

```bash
nvm install 24
nvm use 24
node --version
```

현재 셸이 v24.x.x를 출력하는지 확인한다. 이미 Node 24를 사용 중이라면 중복 설치는 불필요하다. `nvm`이 없으면 임의의 설치 스크립트를 실행하지 말고 사용 중인 버전 관리 도구부터 확인한다. 전역 기본 버전은 바꾸지 않는다. 이미 실행 중인 Node 프로세스는 자동으로 변경되지 않는다.

이 단계만으로 Docker·다른 터미널까지 바뀌지는 않는다. 다음 A-2에서 저장소의 버전 고정을 진행한다.

### A-2. 저장소 버전 고정과 기존 서버 회귀 확인

- `.nvmrc`에 검증된 정확한 Node 24 패치 버전을 기록한다.
- CI와 Docker의 두 stage도 같은 지원 버전 계열로 맞추고 Docker 패치/이미지 digest 정책을 정한다. Docker 이미지를 무조건 latest로 지정하지 않는다.
- lockfile을 유지한 `npm ci`로 네이티브 의존성도 새 런타임에서 설치하고 lint/build/test를 수행한다.
- 현재 CI의 `npm test` 단계는 주석 처리되어 있다. CI 성공이 단위 테스트 통과라는 뜻은 아니다. 기존 실패를 기록하고 관련 테스트부터 복구한다.
- DB 동기화·SSL 환경을 바꾸지 않는다. 런타임 정렬을 이유로 운영 환경변수로 실행하지 않는다.

### A-3. 메트릭 패키지 확정·설치

현재 공식 저장소는 기존 `prom-client`에서 `@prometheus-io/client`로 이름 변경을 안내한다. 확인한 공식 main의 Node 조건은 `^22 || ^24 || >=26`이다. main 문서와 npm 배포 버전은 다를 수 있으므로 설치 전에 실제 배포 메타데이터를 조회한다. [공식 클라이언트](https://github.com/prometheus/client_js)

```bash
npm view @prometheus-io/client version engines
```

- 게시된 버전의 변경 이력·타입 API·Node 조건을 확인한 뒤 해당 버전을 `--save-exact`로 설치하고 lockfile을 함께 관리한다.
- 조회 실패 시 미배포/네트워크/권한 문제를 구분한다. 모르는 버전을 추측해 설치하지 않는다.
- 별도 Nest 래퍼는 처음에는 추가하지 않고 Registry·Counter·Histogram 역할을 직접 학습한다.

### A-4. MetricsModule과 MetricsService

예정 폴더는 아래와 같다. 아직 생성된 소스 파일이 아니다.

```text
src/metrics/
├── metrics.module.ts
├── services/metrics.service.ts
├── middleware/http-metrics.middleware.ts
├── controllers/metrics.controller.ts
└── guards/metrics-access.guard.ts
```

- 서비스가 전용 Registry와 지표를 한 번 생성한다. 요청마다 새 Registry를 만들지 않는다.
- Nest DI로 주입하며 테스트마다 Registry를 분리해 중복 등록 오류를 막는다.
- HTTP 계측에는 DB Repository가 필요 없다. DB에 요청별 통계 행을 동기 저장하지 않는다.
- 기본 프로세스 메트릭부터 확인한다. Linux 전용 지표는 macOS에서 없을 수 있다.

### A-5. HTTP 요청 계측

- 전역 미들웨어로 요청 시작 시 단조 시계를 기록한다. Nest Guard보다 앞에서 들어가 401·403·429도 관찰한다.
- 응답 `finish` 시 최종 statusCode로 완료 요청과 지연을 기록한다. 소켓으로 데이터를 넘긴 시점이지 사용자 화면 표시 완료 시점은 아니다.
- `close`가 완료 전 발생하면 중단 요청으로 구분한다. finish/close에서 이중 집계되지 않게 한다.
- inflight 증감은 모든 종료 경로에서 맞춰 음수·누적 누수를 막는다.
- 정상 route template은 라우팅 이후 얻는다. 등록 시점에 req.route가 없다고 실제 URL을 label로 저장하지 않는다.
- WebSocket upgrade/SSE 연결은 일반 요청 시간과 분리한다. 초기에는 대상 REST API만 지연 비교하고 장기 연결은 별도 지표로 확장한다.

미들웨어와 서비스 단위 테스트 후 Nest 통합 테스트에서 Guard/404/ValidationPipe 오류도 확인한다. Controller 인터셉터만으로 전체 거부 요청을 수집했다고 가정하지 않는다. [Nest 미들웨어](https://docs.nestjs.com/middleware)

### A-6. /metrics 접근 보호

- HTTP Controller는 Registry의 결과를 올바른 content type으로 반환한다.
- 로컬 전용 서버에서만 초기 확인한다. 일반 API가 모든 인터페이스에 바인딩되어 있다면 localhost URL을 쓴다는 이유로 내부 전용이 되는 것은 아니다.
- Prometheus 전용 인증 또는 별도 내부 포트·망 제한을 갖춘다. 관리용 로그인 JWT의 짧은 만료에 의존하지 않는다.
- 스크레이프 인증 정보는 환경변수/secret으로 관리하고 저장소·로그에 남기지 않는다.
- 보호된 수집 요청에 한해 rate-limit 예외를 적용한다. 전체 API Guard를 제거하지 않는다.
- /metrics 자체는 업무 API 카운터·지연에서 제외한다. 요청별 DB 쿼리를 실행하는 무거운 metrics 응답도 피한다.

### A-7. 로컬 Prometheus·Grafana

- 별도 Compose 파일·볼륨으로 실행하고 호스트 포트는 loopback에 바인딩한다. 기존 PostgreSQL/Redis 볼륨은 변경하지 않는다.
- Docker 컨테이너의 localhost는 호스트 NestJS가 아니다. 호스트 경유 주소 또는 같은 네트워크의 서비스 이름을 실제 배치에 맞춰 선택한다.
- 로컬 학습 시작안은 수집 5초, 관찰 5분 이상이다. 운영값으로 그대로 복사하지 않는다. 기존 30초 부하 테스트는 처리량 탐색용이며 경보 평가에는 짧을 수 있다.
- Prometheus target UP과 시간에 따라 증가하는 요청 카운터를 확인한다. 재시작 후 counter reset은 정상이며 rate 계산에서 고려한다.
- Grafana에서 API별 RPS, 정상/실패 지연, 5xx, 429, inflight, 메모리·CPU·이벤트 루프 지연을 본다.
- 보존기간·디스크 상한·컨테이너 메모리 한도를 정한다. 무료 소프트웨어라도 실행·저장 자원은 소모된다.

### A-8. 계측 검증과 경보

검증된 테스트 환경에서 요청 수를 알고 있는 작은 샘플로 시작한다.

| 사례 | 기대 결과 |
| --- | --- |
| 정상 200 요청 N회 | 업무 카운터 정확히 N 증가 |
| 잘못된 DTO 400 / 인증 거부 401·403 | 최종 응답 코드로 집계 |
| 존재하지 않는 글·경로 404 | 제한된 template/unmatched label 사용 |
| 요청 제한 429 | 5xx와 별도 표시, 정상 처리량에서 제외 |
| 통제된 테스트 핸들러의 500 | 오류율 증가와 경보 발동 확인 |
| 완료 전 연결 종료 | 성공 200으로 기록되지 않고 중단 집계 |
| metrics 수집 반복 | 업무 요청 수 증가 없음 |
| 동일 경로의 다양한 글 ID | ID 수만큼 새 시계열이 생기지 않음 |

실제 고객용 에러 유도 엔드포인트는 만들지 않는다. 500·지연 시나리오는 자동 테스트 또는 격리된 테스트 전용 구현으로 제한한다. 경보는 충분한 표본·지속 시간 조건을 두고 발동뿐 아니라 회복 후 해제도 확인한다.

### A-9. DB·캐시·큐 지표 확장

HTTP 지연만으로 DB 병목을 단정하지 않는다. 실제 query 시간과 연결 대기, Redis 적중/실패, 큐 backlog와 가장 오래된 작업 대기시간을 순서대로 추가한다. 설치한 드라이버의 지원 계측 API를 우선하고 TypeORM 내부 private 필드에 무리하게 결합하지 않는다.

## 5. 최초 메트릭 계약

| 예정 메트릭 | 유형 | 측정 의미 |
| --- | --- | --- |
| loop_http_requests_total | Counter | 완료한 REST 요청 수, method/route/status_code |
| loop_http_request_duration_seconds | Histogram | 서버 내부 관찰 요청 완료 시간, 같은 제한된 label |
| loop_http_requests_in_flight | Gauge | 현재 진행 요청 수, 라우팅 전이라 처음에는 경로 label 없이 관리 |
| loop_http_requests_aborted_total | Counter | 완료 전 종료된 요청, 200 성공과 분리 |
| Node 기본 프로세스 지표 | 라이브러리 기본 | 메모리·CPU·이벤트 루프 등, 서버 호스트 전체 자원과 구분 |

- label은 `/posts/:id`, `/posts/:id/comments`처럼 고정된 route template을 사용한다. 404 fallback은 `unmatched` 같은 제한된 값으로 둔다.
- 사용자 ID·게시글 ID·전체 URL·cursor·검색어·requestId·오류 메시지는 label 금지다. method도 예상 집합 밖은 OTHER로 정규화한다.
- requestId는 개인정보를 제거한 로그/trace에서 연결한다. metric 시계열을 요청마다 만들지 않는다.
- 초 단위 Histogram bucket 초안: 0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10. 실제 목표와 분포를 보고 조정한다.
- p95/p99는 충분한 관찰 창의 Histogram에서 추정한다. 합계/건수는 평균이지 p99가 아니다. 서버 인스턴스별 percentile을 단순 평균하지 않는다.
- 이번 입문 구현은 지원이 확인된 명시적 bucket Histogram부터 시작한다. native histogram은 패키지·Prometheus·대시보드 호환성을 별도로 검증한 뒤 도입한다.

label 수와 계측 비용은 제한되어야 한다. 수집 코드 실패가 업무 요청을 실패시키지 않도록 설계한다. [Prometheus 계측 가이드](https://prometheus.io/docs/practices/instrumentation/)

## 6. B단계: 인기 게시글 부하 훈련

1. 전용 테스트 DB·Redis·서버 대상과 외부 호출 차단을 확인한다.
2. 테스트용으로 실제 존재하는 postId와 댓글 데이터를 선정한다. ID를 운영 코드에 하드코딩하지 않는다.
3. 목록·상세·댓글 API의 캐시 적용 여부와 지연 분포를 각각 확인한다. 목록 캐시가 상세에도 적용된다고 가정하지 않는다.
4. 전역 ThrottlerGuard 정책 검증과 용량 측정을 분리한다. 운영 제한을 비활성화하지 않는다.
5. 단계별 연결 부하→인기 ID 집중/분산→지속 유입률→순간 급증으로 확장한다.
6. 같은 부하 중 Flutter 앱의 진입·댓글 스크롤을 반복한다. 에뮬레이터는 기능 확인용이며 최종 프레임 수치는 실기기 profile에서 확인한다.
7. 정상 처리량·p99·오류율·DB 대기·자원 포화를 함께 보고 원인 하나씩 개선한다.
8. 부하 제거 후 대기열·응답 시간이 회복되는지도 기록한다.

실행 명령과 기록표는 [기존 부하 테스트 문서](posts-load-test.md)를 재사용한다. 일정 도착률 테스트와 혼합 행동 스크립트는 나중에 k6로 추가한다. 계측 자체의 오버헤드도 작은 동일 부하에서 전후 비교한다.

## 7. C~G단계: 운영 문제를 재현하며 확장

### 동시 작성

- 같은 작성 의도를 멱등 키로 식별하고 사용자·작업·키의 DB unique 제약과 짧은 트랜잭션을 설계한다.
- 연타 차단만으로 여러 기기/재시도의 중복을 막았다고 판단하지 않는다.
- 같은 키·다른 payload, 저장 후 응답 유실, 일부 성공을 테스트한다. 응답 불명은 DB 최종 상태로 대조한다.
- AI 요약·알림 후속 처리 분리 여부는 API 계약과 복구 정책을 먼저 정한다. HTTP 성공을 실제 푸시 수신으로 간주하지 않는다.

### 큐·장애 복구

- DB 저장과 큐 등록 사이 유실은 outbox 등으로 보완하고, 재시도되는 작업의 부작용을 멱등 처리한다.
- 테스트 워커 중단/재시작으로 적체 감지→복구→중복 여부 확인을 수행한다.
- 실패 횟수·최종 실패 보관·재처리 권한·감사 기록을 설계한다.

### 데이터·배포

- 격리 DB 백업을 실제로 복원하고 RPO(허용 데이터 손실), RTO(목표 복구 시간)를 검증한다.
- 스키마 변경은 신구 앱/서버가 공존하는 expand→migrate→contract 순서를 검토한다. 운영 synchronize에 의존하지 않는다.
- CI 테스트 복구, 점진 배포, 기능 플래그, 롤백 조건, 구버전 앱 계약 테스트를 구현한다.
- DB 변경은 애플리케이션 롤백만으로 되돌릴 수 없는 경우가 있으므로 별도 복구안을 둔다.

### 운영 훈련

- 알림 발생→영향 범위 확인→완화→원인 분석→재발 방지 회고를 한 번의 실습으로 기록한다.
- 고객 영향 지표로 SLO와 경보를 설정한다. p99 숫자나 CPU 임계값을 근거 없이 만능 기준으로 쓰지 않는다.
- 데이터 정확성, 보안, 관찰 비용, 외부 서비스 비용도 성능과 함께 평가한다.
