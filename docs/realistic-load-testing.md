# 가짜 사용자 기반 실서비스 성능·장애 테스트 계획

작성: 2026-10-19. 상태: 설계 문서. 이 문서 작성으로 테스트 서버, 더미 데이터, k6 스크립트, 메트릭 수집이 구현되거나 실행된 것은 아니다.

## 1. 목표

실제 사용자가 없는 상태에서 가짜 계정·게시글·댓글과 가상 사용자 행동으로 Loop의 처리 한계, 데이터 정합성, 과부하 후 회복을 확인한다.

가짜 응답을 빠르게 반환하는 테스트가 아니라 실제 HTTP Controller, JWT 인증, 권한 검사, ValidationPipe, Service, TypeORM, PostgreSQL, Redis를 통과하는 요청을 만든다. 비즈니스 경로는 실제 코드를 사용하고 외부 메시지·유료 API는 명시적으로 대역 처리한다.

로컬에서 유명 서비스와 동일한 운영 환경이나 수용 인원을 보장할 수는 없다. 다음 두 수준을 구분한다.

- 로컬 기능·병목 재현: 데이터 분포, 동시 접근, 실패 조건과 복구를 학습한다.
- 운영 유사 용량 검증: 서버 사양·프로세스 수·DB·Redis 버전·설정·네트워크·TLS·프록시 구성을 고정하고 별도 부하 생성기로 측정한다. 실제 운영 데이터를 사용할 필요는 없다.

누적 가입자, 동시 접속자, HTTP 연결, 가상 사용자(VU), 초당 요청, 초당 사용자 시나리오 시작 수는 서로 다른 값이다. 다운로드 수나 더미 계정 수를 서버 수용량으로 환산하지 않는다.

## 3. 테스트 환경 구성 계획

```text
k6 부하 생성기 ──────┐
Flutter 테스트 앱 ──┼─→ 성능 테스트 전용 NestJS HTTP 서버
관리자 웹(후속) ────┘          ├─ PostgreSQL performance DB
                              ├─ Redis performance 인스턴스
                              ├─ BullMQ 전용 큐·워커(큐 시나리오)
                              └─ FCM / OpenAI / S3 테스트 대역
                                    ↓
                         HTTP·DB·프로세스·큐 지표 기록
```

- Compose 프로젝트·서버 포트·DB 이름·계정·Redis·큐 이름·볼륨을 개발/통합/운영과 분리한다.
- 지속 측정과 재시작 복구에는 전용 볼륨을 사용하고, 메모리 기반 tmpfs 결과와 비교하지 않는다.
- 시드·초기화·마이그레이션·부하 실행 전에 대상 host/port/DB/current_user 등 비밀이 아닌 식별값을 검사한다. 허용 대상 불일치 시 즉시 실패시킨다.
- 첫 실행은 루프백 주소에만 바인딩한다. 별도 머신에서 부하를 줄 때는 테스트망 접근만 허용한다.
- watch 없이 컴파일된 코드로 측정한다. Node·Docker 자원 제한·DB pool·타임아웃·캐시 TTL을 실행 기록에 남긴다.
- `NODE_ENV=production`을 성능 향상 스위치처럼 사용하지 않는다. 기존 `.env.production`, DB SSL·시크릿·외부 서비스 설정이 연결될 수 있다.
- 전용 설정 파일은 시작 코드가 명시적으로 읽도록 구현해야 한다. `.env.performance`라는 파일을 만드는 것만으로 자동 적용되지는 않는다.
- 테스트 서버를 별도 조립하면 실제 Module·Guard·Pipe와 부팅 순서를 재사용하고, 제외/대체한 경계를 결과에 기록한다. 전체 AppModule와 같다고 표현하지 않는다.
- 운영 유사 단계에서는 프록시·TLS·인증 흐름까지 포함한다. 관리자 BFF 부하는 이후 Next.js를 경유하는 별도 시나리오로 측정한다.

### 외부 서비스 격리

- 가짜 사용자라고 FCM·AI·업로드 요청이 자동 차단되지는 않는다. 특히 게시글 작성은 AI·알림 경로를 실행한다.
- 테스트용 Provider로 외부 어댑터를 대체하고 테스트 프로세스에 운영 자격증명을 주입하지 않는다. 가능하면 외부 송신도 제한한다.
- 게시글 핵심 DB 부하 측정에서는 AI·알림 대역을 사용하고 제외된 비용을 명시한다.
- 큐 부하 측정에서는 실제 BullMQ·워커·재시도를 실행하되 최종 FCM 송신만 대역 처리한다. 이 둘을 같은 결과로 합치지 않는다.
- 외부 서비스의 지연·오류를 다룰 때는 대역에 제한된 지연·실패율을 넣는다. 실제 공급자 성능이나 단말 수신을 검증한 것으로 보고하지 않는다.

## 4. 현실적인 데이터 생성

처음부터 최대 규모를 넣지 않고 데이터 크기와 트래픽을 별도 축으로 늘린다. 아래 숫자는 학습 시작안이며 장비 용량과 생성·조회 비용에 따라 조정한다.

| 단계 | 가짜 사용자 | 게시글 | 댓글 | 목적 |
| --- | ---: | ---: | ---: | --- |
| 스모크 | 100 | 1,000 | 3,000 | 시드·로그인·시나리오가 정상 작동하는지 |
| 기본 | 1,000 | 10,000 | 30,000 | 기존 데이터 규모와 비교 가능한 기준선 |
| 확장 | 10,000 | 100,000 | 300,000 | 인덱스·캐시·개인별 조회와 쓰기 경합 |
| 선택적 대량 | 100,000 | 1,000,000 | 별도 산정 | 디스크·메모리·쿼리 변화 확인 후 선택 실행 |

### 시드에 포함할 분포

- 대부분은 읽기 위주, 일부는 작성·댓글이 많은 계정으로 만든다.
- 인기 글·최근 글·오래된 글·댓글이 많은 글·댓글 없는 글을 구분한다.
- 요청 일부가 소수의 인기 ID에 집중되도록 하고, 전체 ID 무작위 접근과 별도로 비교한다.
- 본문 길이와 작성 날짜를 다양하게 한다. 모든 글을 같은 짧은 본문·동일 시각으로 만들지 않는다.
- 일반 계정과 소수 테스트 관리자 계정을 구분한다. 이메일은 `example.invalid` 같은 테스트용 도메인을 사용한다.
- 실제 로그인 테스트용 계정에는 서버와 동일한 방식의 유효한 비밀번호 해시가 필요하다. 고비용 해싱을 매 요청마다 수행하지 않는다.
- 쿠폰은 활성·비활성·시작 전·종료·품절 이벤트와 기발급·미발급 계정을 구분해 만든다.
- 난수 seed·실행 ID·실제 생성 개수·데이터 크기를 기록해 같은 분포를 다시 만들 수 있게 한다.
- 생성은 제한된 배치와 동시성으로 실행한다. 백만 개 객체를 한꺼번에 메모리에 만들지 않는다.
- 데이터 생성과 마이그레이션을 구분한다. `synchronize:true`로 기존 테이블을 자동 수정하지 않는다.
- 삭제/초기화는 전용 DB와 해당 실행 데이터임을 확인한 명시적 작업으로만 수행한다. 기존 개발 seed 초기화를 재사용하지 않는다.

가짜 계정 10만 명을 만드는 것과 10만 명이 동시에 요청하는 것은 다른 실험이다.

## 5. 가상 사용자·인증 설계

API 부하 도구는 실제 사람이나 모바일 렌더러를 생성하지 않는다. 사용자마다 계정·인증·조회 위치를 구분하고 API 행동을 재현한다.

### 인증 시나리오를 둘로 분리

1. 기능 API 부하: 테스트 시작 전 계정별 유효 토큰을 준비해 로그인 비용과 분리한다. 실제 Guard 검증은 유지한다.
2. 로그인·갱신 부하: 실제 `/auth/login`, `/auth/refresh`를 별도 측정한다. 비밀번호 검증·세션 저장의 병목을 확인한다.

- 테스트 전용 키로 사전 서명하는 방식은 기능 API 검사에서만 사용할 수 있으며, 로그인 발급 흐름을 검증했다고 보고하지 않는다.
- 서명 키는 테스트 서버 전용으로 사용한다. 운영 Guard에 우회 코드나 공개 토큰 생성 API를 만들지 않는다.
- 토큰 만료 시간을 테스트 길이와 맞춘다. 장시간 테스트는 실제 갱신·실패·재로그인 정책을 포함한다.
- 같은 사용자의 Refresh Token을 여러 가상 사용자가 동시에 공유하지 않는다. 의도적인 갱신 경합은 별도 시나리오로 둔다.
- 비밀번호·JWT·개인정보·전체 응답 본문은 결과나 로그에 기록하지 않는다.

### 첫 혼합 행동안

사용자 시나리오 시작 비율의 예시이며 실사용 분석값은 아니다. 각 시나리오가 여러 API를 호출하므로 HTTP 요청 비율과 같지 않다.

| 비율 | 사용자 행동 |
| ---: | --- |
| 70% | 목록 → 서버 응답 커서로 다음 페이지 → 게시글 상세 → 댓글 목록 |
| 20% | 다양한 검색어 → 결과의 실제 게시글 상세 |
| 10% | 본인 게시글 또는 댓글 작성 → 반환 ID로 조회·내용 확인 |

작성 범위·응답 DTO는 스크립트 구현 직전 실제 Controller와 확인한다. 읽기만 실행하는 기준선부터 만든 뒤 쓰기를 추가한다.
쿠폰 경합, 로그인 폭증, WebSocket·SSE 장기 연결은 혼합 부하와 분리해 원인을 관찰한다. 향후 종합 시나리오에서 함께 실행한다.

## 6. 부하 모델과 실행 순서

기본 도구 후보는 k6다. 아직 설치하거나 스크립트를 등록하지 않았다. 기존 autocannon은 단일 읽기 기준선에 계속 사용할 수 있다.

| 유형 | 확인할 문제 |
| --- | --- |
| 스모크 | 소수 계정으로 정상 인증·본문·커서·ID 처리 확인 |
| 일정 VU | 정해진 수의 가상 사용자들이 행동을 반복할 때 지연·처리량 |
| 도착률 증가 | 응답이 느려져도 새 시나리오가 계속 시작될 때 대기 증가 |
| 순간 급증 | 평상시 유입에서 갑자기 증가한 뒤 정상 수준으로 돌아오는 과정 |
| 지속 부하 | 일정 부하를 오래 유지했을 때 메모리·연결·큐 적체 누적 |
| 장애·회복 | 워커/캐시/DB 지연 등의 실패 후 데이터와 처리량 회복 |

- 일정 VU는 응답이 느리면 새 요청 발생도 줄어들 수 있다. 일정·증가 도착률 테스트와 함께 본다.
- k6 도착률은 요청 개수가 아니라 iteration 시작 수다. 한 iteration의 API 개수·대기 시간과 실제 RPS를 함께 기록한다.
- 스모크 1~5 VU로 시작한다. 도착률 예시는 초당 1 → 5 → 10개 사용자 시나리오이며, 앞 단계가 안정적일 때만 높인다.
- 워밍업과 측정 구간을 분리하고 각 구간을 충분히 유지한다. 짧은 탐색 후 5~10분 기준선, 30분 이상 지속 부하는 자원을 확인한 뒤 선택한다.
- 부하 생성기의 CPU·메모리, 사용 VU, dropped_iterations를 기록한다. 도구가 목표 유입량을 만들지 못한 결과를 서버 처리 한계로 단정하지 않는다.
- 같은 조건을 가능한 한 여러 번 비교하고 변경은 한 번에 하나만 적용한다. 캐시 적중·미적중·만료 구간과 데이터 편중을 구분한다.
- 로컬의 서버와 부하 생성기는 자원을 경쟁한다. 최종 용량 측정은 별도 부하 머신을 사용하고 서버·DB 배치를 기록한다.

### 요청 제한을 별도로 검증

- 보호 정책 시나리오는 제한을 유지하고 예상 429를 확인한다.
- API 처리량 측정은 격리된 성능 서버에서 대상·범위를 정해 제한을 조정한다. 인증·인가·입력 검증은 유지한다.
- 현재 `LOAD_TEST_MODE`는 development에서만 적용되고 전역 제한을 생략한다. 전용 설정이 같은 동작을 한다고 가정하지 않는다.
- 실제 코드와 테스트에 따라 전용 설정을 확정하고 외부 공개 서버에서 제한을 풀지 않는다. 가짜 IP 헤더로 우회하지 않는다.

## 7. 관찰 지표와 합격 기준

지표 수집이 준비되기 전에는 본격 부하를 시작하지 않는다. k6가 관찰한 클라이언트 지연과 서버 내부 소요 시간은 별도로 비교한다.

| 영역 | 필요한 지표·검증 |
| --- | --- |
| HTTP | API별 정상 처리량, p50/p95/p99, 타임아웃, 상태 코드, 응답 구조·ID·본문 일치 |
| NestJS/Node | CPU, RSS/heap 추이, 이벤트 루프 지연, 연결·열린 핸들, GC 영향 |
| PostgreSQL | 쿼리 실행 시간·실행 계획, pool 대기, 활성 연결, 잠금 대기·교착, 디스크 I/O |
| Redis | hit/miss, 응답 시간, 메모리·eviction, 캐시 만료 시 DB 부하 |
| BullMQ | 대기·활성·완료·실패 개수, 가장 오래된 작업 나이, 재시도와 소비 속도 |
| 데이터 | 생성 누락·중복, 작성자/본문 일치, 쿠폰 발급량과 실제 행 수 대사 |
| 복구 | 부하 제거·의존성 복원 후 지연·큐가 기준 수준으로 회복되는 시간 |
| 부하 도구 | 생성기 자원, 실제 도착률, VU 상한, dropped_iterations |

- 학습용 시작 기준 예시: API별 p95 500ms 미만, 예상 밖 실패율 1% 미만, 초과 발급 0건, 데이터 정합성 오류 0건. 실제 요구사항·실험 환경에 맞게 조정하고 합의한 값을 결과에 기록한다.
- DB/인프라가 다른 실험에 동일 기준을 무조건 적용하지 않는다. 데이터 정확성은 빠른 응답과 별개로 검사한다.
- 200이어도 빈 오류 페이지·잘못된 데이터면 성공이 아니다. 401/403/429 폭증을 높은 성능으로 보고하지 않는다.
- 의도적인 쿠폰 품절·중복 발급·요청 제한의 예상 비즈니스 결과는 별도 카운터로 분리한다. 5xx·타임아웃을 품절로 분류하지 않는다.
- 엔드포인트별 결과를 남긴다. 빠른 목록 캐시가 느린 쓰기 API를 전체 평균에서 가리지 않게 한다.
- 전체 사용자 ID·JWT·자유 검색어를 메트릭 라벨로 사용하지 않는다. 경로 패턴·메서드·상태 코드 등 제한된 라벨을 사용한다.

## 8. 쿠폰 및 쓰기 정합성 시나리오

쿠폰 상세 계획은 [기존 쿠폰 가이드](limited-coupon-events.md)를 따른다.

- 재고보다 많은 서로 다른 계정이 같은 이벤트에 발급 요청 → 성공한 고유 발급 수가 재고 이하인지 확인.
- 같은 계정의 동시 재요청 → 동일 이벤트의 계정당 발급 행 1개 확인. 기존 쿠폰 반환은 정상 동작일 수 있음.
- 종료·비활성 전환 중 요청 → 서버의 트랜잭션·시각 기준에 맞는 결과인지 확인.
- 응답 유실·타임아웃 → 무조건 재발급하지 않고 본인 발급 조회로 최종 결과 확인.
- 측정 후 `issuedCount`, 발급 행 수, 계정별 중복, 초과·음수 수량을 대사.

일반 게시글·댓글 생성 POST가 멱등하다고 가정하지 않는다. 응답 유실 후 자동 반복은 중복 생성을 만들 수 있다.
테스트가 중복을 발견하면 실패를 기록하고 기능별 멱등 계약을 설계한 뒤 재검증한다. 테스트를 통과시키려고 오류를 숨기지 않는다.

## 9. 장애와 Flutter 검증

격리 환경에서만 한 번에 한 조건을 주입하고, 의존성을 복원한 뒤 회복까지 기록한다.

- Redis 지연·중단: API 실패 또는 fallback이 실제 정책과 맞는지, 복원 후 회복하는지.
- 워커 중단·재시작: 큐 적체가 보이고 미완료 작업이 복구되는지, 중복 부작용이 생기는지.
- DB 제한·지연: 연결 대기·쿼리 타임아웃이 제한 시간 안에 응답으로 드러나는지.
- 서버 처리 후 응답 유실: 클라이언트의 미확정 처리와 데이터 최종 상태가 일치하는지.

가상 사용자 API 부하와 함께 실제 Flutter 앱 한두 대에서 목록 스크롤·상세 이동·댓글 작성·쿠폰 발급을 확인한다.
에뮬레이터는 기능 재현과 네트워크 관찰에 사용한다. 프레임·메모리 기준선은 지원되는 실기기의 profile 모드에서 DevTools로 측정한다.
API 지연과 UI/raster 프레임 시간을 분리한다. 서버가 느려도 로딩 표시·스크롤·취소·화면 이동이 과도하게 막히지 않는지 확인한다.

네트워크 지연·본문 크기·동시 응답의 JSON 변환·목록 재빌드를 앱 측에서 따로 측정한다. 서버 처리량만으로 프레임 드랍이 없다고 결론 내리지 않는다.

## 10. 단계별 작업과 완료 조건

아래 파일명은 예정이며 명령 등록·구현 완료를 의미하지 않는다.

| 단계 | 작업·예정 위치 | 완료 증거 |
| --- | --- | --- |
| 1 | `docker-compose.performance.yml`: 전용 DB·Redis와 자원·포트 설계 | 개발/통합 환경과 저장소·포트 비공유, healthcheck |
| 2 | `test/performance/`의 설정·부팅 진입점: 실제 경로와 외부 어댑터 격리 | 명시적 대상 검사, 외부 송신 없이 단일 실제 API 성공 |
| 3 | 성능 전용 스키마 준비·마이그레이션 | 필요한 테이블·인덱스·제약 확인, 개발 DB 변경 없음 |
| 4 | `test/performance/seed.ts`: 실행별·재현 가능한 계정·게시글·댓글 | 분포·개수·인증 가능 계정 확인 |
| 5 | `test/performance/k6/`: 사용자 데이터·인증·읽기 스모크 | 실제 응답 커서·ID·인증 검사 통과 |
| 6 | HTTP·DB·Node·Redis 계측과 기준선 | 실제 지표와 환경·캐시 조건 기록 |
| 7 | 혼합 읽기·쓰기, 증가·급증 부하 | API별 p95/p99·정상 처리량·실패율과 원인 가설 |
| 8 | 쿠폰 경합·데이터 대사 | 초과·중복·누락 여부 수치와 최종 결과 확인 |
| 9 | 큐·캐시·서버 장애와 지속 부하 | 재시작 복구·큐 배출·메모리 추이 기록 |
| 10 | Flutter 병행 확인·개선 전후 비교 | 같은 조건의 재측정, 앱 지표, 후속 조치와 한계 |

패키지 설치나 리소스 실행은 각 단계에서 현재 환경을 확인한 뒤 진행한다. 이 문서에 미구현 실행 명령을 복사해 실행하는 절차는 두지 않는다.

## 11. 중단·정리 및 결과 기록

- 목표 DB·Redis 불일치, 외부 발송/유료 호출, 대량 예상 밖 오류, 장비 메모리 압박, 설정한 지연·큐 상한 초과 시 부하를 중단한다.
- 먼저 요청 유입을 멈추고 진행 중 요청·큐와 서버 상태를 확인한다. 과부하 상태에서 무제한 재시도하지 않는다.
- 데이터 정합성 대사와 로그·지표 저장을 마친 뒤 테스트 설정을 복구한다. 볼륨 삭제나 전체 캐시 초기화는 별도 명시적 작업이다.
- 결과에 토큰·패스워드·개인정보를 남기지 않는다. 초기화·마이그레이션·부하 기록을 코드·커밋·시드 실행 ID와 연결한다.

실험별 기록 양식:

```text

Node·패키지·이미지 버전:
데이터 수·크기·인덱스·분포:
실제 인증 경로 / 제외·대체한 외부 경로:
```
