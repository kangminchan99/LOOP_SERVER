# 사용자 차단·해제와 콘텐츠 페이지네이션 설계

작성: 2026-10-27. 상태: 문서 단계. 차단 엔티티·API·조회 필터·앱 화면은 아직 구현하거나 검증하지 않았다.

## 1. 기능 범위와 정책

로그인한 사용자가 특정 계정을 차단하면 본인 화면의 해당 사용자 콘텐츠를 제외한다. 설정의 차단한 사용자 목록에서 해제할 수 있다. 게시글·검색·댓글의 제외는 서버 SQL에서 페이지네이션 전에 적용한다.

아래는 A가 B를 차단한 경우의 초기 정책이다.

| 영역 | 동작 |
| --- | --- |
| A의 게시글 목록·검색 | B의 게시글 제외 |
| A의 게시글 상세 접근 | B의 글은 본문 없이 일반적인 404 응답 |
| A의 댓글 조회 | B의 댓글 제외. B의 게시글 아래 댓글 API도 부모 게시글 접근 정책 적용 |
| A의 내 댓글 목록 | B의 게시글에 쓴 내 댓글은 목록에서 제외. 댓글 원본은 삭제하지 않음 |
| A의 차단 목록 | B의 최소 프로필과 해제 버튼 표시. 이 목록에는 차단 필터를 적용하지 않음 |
| 차단 해제 | 현재 차단 관계 삭제 후 첫 페이지부터 재조회. 원래 콘텐츠를 새로 생성하지 않음 |
| B의 일반 공개 콘텐츠 조회 | B가 A를 차단하지 않았다면 기존 정책 유지. 양방향 콘텐츠 비공개로 확대하지 않음 |
| 비로그인 공개 조회 | 기존 공개 조회 유지. 로그인 차단 설정은 공개 글 자체의 접근 비밀성을 보장하지 않음 |
| 1:1 채팅 | 어느 한쪽이 차단하면 양쪽의 신규 방 생성/기존 방 반환, 방 입장·과거 메시지 조회·신규 전송을 제한하고 방 목록·미리보기에서 제외. 기록은 유지 |
| 사용자 게시글 알림 | 수신자가 차단한 작성자의 신규 알림·푸시 제외. 저장된 목록·미읽음 수에서도 같은 조건 적용 |
| 관리자 운영 API | 개인 차단 관계로 관리자 검수 목록을 숨기지 않음. 기존 관리자 권한 유지 |

차단을 상대방에게 직접 통지하지 않는다. 채팅 거절 안내에도 누가 누구를 차단했는지 포함하지 않는다.
차단은 계정 정지·탈퇴·신고와 다르다. 사용자·게시글·댓글·채팅 기록을 삭제하거나 관리자 역할을 변경하지 않는다.
초기 채팅 범위는 현재 DIRECT 1:1이다. 향후 그룹 채팅에 같은 정책을 그대로 적용하지 않는다.
시스템 공지·전체 운영 알림은 작성자 차단과 구분한다.

기존 통합 테스트는 모듈 조립·엔티티 목록을 직접 지정한다. 새 의존성을 실제 테스트에 등록해야 하며, 기존 테스트가 자동으로 차단을 검증한다고 가정하지 않는다.

## 3. 데이터 모델

예정 폴더: `src/user-blocks/`.

| 필드 | 의미 |
| --- | --- |
| id | 차단 관계 ID, PostgreSQL integer |
| blockerId | 차단을 실행한 사용자 ID. 인증에서 결정 |
| blockedUserId | 차단 대상 사용자 ID |
| createdAt | 서버 기준 차단 시각, timestamptz(3) |

예정 테이블명: `user_blocks`.

- UNIQUE `(blockerId, blockedUserId)`: 반복·동시 요청으로 차단 관계 중복 생성 방지.
- CHECK `blockerId <> blockedUserId`: 자기 자신 차단 방지.
- 두 사용자 FK는 `users(id)`를 참조하며 사용자 삭제 시 관계 행만 CASCADE 정리한다. 차단 때문에 사용자나 콘텐츠가 삭제되는 관계를 만들지 않는다.
- `(blockerId, createdAt DESC, id DESC)` 인덱스: 내 차단 목록 커서 조회.
- UNIQUE 인덱스는 조회자의 특정 작성자 차단 여부 확인에 사용한다. 역방향 조회·계정 삭제용 추가 인덱스는 실제 실행 계획과 규모를 보고 검토한다.
- A→B와 B→A는 서로 다른 관계다. 한쪽 해제가 상대방의 차단까지 삭제하지 않는다.

마이그레이션은 신규 테이블·제약·인덱스만 추가한다. users나 다른 기존 테이블 재생성 SQL이 포함되지 않았는지 검토한다. 개발 DB에 테스트용 users 생성 마이그레이션을 실행하지 않는다.

## 4. API 계약 계획

차단 API는 모두 실제 JWT와 현재 계정 확인이 필요하다. 본인 ID를 body/query로 받지 않는다. 대상 ID는 양의 PostgreSQL integer 범위로 검사한다.

| 메서드 | URL | 동작·성공 응답 |
| --- | --- | --- |
| PUT | `/users/me/blocks/:targetUserId` | 차단 또는 기존 관계 유지, 200과 `{ blockedUserId, blockedAt }` |
| DELETE | `/users/me/blocks/:targetUserId` | 본인 차단 관계 해제. 이미 없어도 본문 없는 204 |
| GET | `/users/me/blocks?limit=20&cursor=...` | 본인이 차단한 사용자 목록, 최신 차단순 커서 |

초기 limit 기본 20·최대 50. GET 응답은 `{ items, nextCursor, hasNext }`로 정하고 각 항목은 `{ blockId, userId, nickname, profileImageUrl, blockedAt }`의 최소 정보만 제공한다. 이메일·비밀번호·상대방의 차단 관계는 반환하지 않는다. nullable 프로필 계약을 명시한다.

- 본인 차단 400, 신규 차단 대상 없음 404, 인증·현재 계정 없음 401, 잘못된 ID·커서 400.
- 반복 PUT은 기존 blockedAt을 유지한다. 단순 save로 목록 순서를 갱신하지 않는다.
- INSERT의 유니크 경합은 기존 관계 반환으로 수렴시킨다. 다른 DB 오류까지 중복으로 숨기지 않는다.
- DELETE는 본인 `(blockerId, blockedUserId)` 조건만 제거한다. 다른 사람의 차단 해제는 허용하지 않는다.
- 상대방 탈퇴 후 유효 ID의 해제 요청은 이미 없는 관계로 처리할 수 있다. 신규 PUT의 대상 존재 검사는 별도로 유지한다.
- 요청 중 대상 탈퇴와 FK 경합은 트랜잭션·필요한 사용자 잠금 또는 오류 매핑으로 처리하고 500을 그대로 사용자에게 노출하지 않는다.
- body 없음 또는 빈 객체만 허용할지 Controller·검증 정책에서 명시한다. blockerId 등 추가 입력은 허용하지 않는다.

## 5. 공개 조회의 선택적 인증

필수 로그인으로 일괄 변경하면 기존 비로그인 게시판이 깨진다. 공개 GET에만 `OptionalJwtAuthGuard`와 optional 사용자 추출기를 별도로 설계한다.

1. Authorization 헤더가 없으면 익명으로 기존 공개 조회.
2. 헤더가 있으면 실제 JWT 검증과 올바른 access 타입 검사.
3. 잘못된·만료 토큰은 401. 검증 실패를 익명 조회로 바꿔 차단 콘텐츠를 다시 반환하지 않음.
4. 로그인한 요청에는 userId를 Service로 전달하고 차단 조건 적용.

필수 인증의 기존 CurrentUser/JwtAuthGuard는 그대로 유지한다. Flutter의 401 갱신 성공 후에는 같은 인증 요청을 재시도하며, 갱신 실패 상태를 비로그인 결과로 덮어쓰지 않도록 세션 전환 정책을 검증한다.
조회자별 응답은 `Cache-Control: private, no-store` 등으로 공용 HTTP 캐시·인증 변경 후 브라우저 캐시가 재사용되지 않게 한다.

## 6. 차단 필터와 페이지네이션

### 게시글 목록·검색

조건 개념 예시(아직 존재하지 않는 테이블·별칭이며 실제 쿼리는 구현 단계에서 확인):

```sql
WHERE NOT EXISTS (
  SELECT 1
  FROM user_blocks b
  WHERE b."blockerId" = :viewerId
    AND b."blockedUserId" = post."authorId"
)
AND /* 검색 조건, 서버 발급 커서 조건 */
ORDER BY post."createdAt" DESC, post.id DESC
LIMIT :limitPlusOne
```

- 차단 제외·검색·커서 조건은 같은 SQL의 WHERE에 적용한다. 작성자별·항목별 추가 쿼리(N+1)를 만들지 않는다.
- TypeORM의 where 재호출은 이전 차단 조건을 덮어쓸 수 있다. 최초 where와 이후 andWhere를 명시적으로 조합한다.
- 게시글은 `(createdAt DESC, id DESC)`, 기존 댓글은 `(createdAt ASC, id ASC)`, 내 댓글은 기존 DESC 정렬을 유지한다.
- 필터링된 결과를 limit+1개 조회한 뒤 앞 limit개를 items로 반환한다. hasNext는 추가 가시 항목의 존재로 계산한다.
- nextCursor는 실제 반환된 마지막 항목의 날짜·ID로 만든다. 숨겨진 글의 마지막 ID나 전체 원본 페이지를 기준으로 만들지 않는다.
- 클라이언트는 서버 커서를 그대로 사용한다. 받은 20개에서 차단된 8개를 지우고 12개·기존 hasNext를 반환하는 방식은 사용하지 않는다.
- 차단 목록도 SQL에서 본인 관계와 커서를 적용한 뒤 limit+1개 조회한다. 별도 COUNT가 꼭 필요하지 않으면 전체 건수 조회를 추가하지 않는다.

### 상세·댓글·내 댓글

- 상세 조회는 존재 여부와 조회자의 차단 관계를 확인해 본문을 반환하기 전에 거절한다. 원본의 실제 삭제와 차단으로 숨김은 내부 로직·테스트에서 구분한다.
- 부모 글이 접근 불가하면 댓글 목록도 404로 처리한다. 댓글 엔드포인트로 본문/작성자 정보를 우회 노출하지 않는다.
- 보이는 글의 댓글 목록에서는 댓글 작성자의 차단 조건을 적용한다.
- 내 댓글은 본인 작성 조건과 부모 글 작성자에 대한 차단 조건을 함께 적용한다. B의 글에 쓴 A의 댓글을 삭제하지 않는다.
- 본인이 작성한 콘텐츠의 관리·삭제 권한은 별도 유지한다. 차단 때문에 소유권 검사를 생략하거나 타인의 삭제를 허용하지 않는다.

### 조회 중 차단·해제와 커서

- 차단·해제 성공 후 영향받는 목록의 커서·누적 목록을 무효화하고 첫 페이지부터 다시 조회한다.
- 차단 해제로 앞쪽에 다시 보이는 글은 기존 커서 이후만 조회하면 빠질 수 있다. 이전 커서를 이어 쓰지 않는다.
- 서버의 날짜·ID 커서는 원본 행이 현재 보이지 않아도 값으로 비교한다. 숨겨진 커서 행을 다시 조회해야만 다음 페이지가 작동하는 구현을 피한다.
- 데이터·차단 관계가 바뀌는 도중의 전체 순회를 스냅샷으로 보장하지 않는다. 불변 조건에서 중복·누락 없음과 변경 후 첫 페이지 재시작을 별도 검증한다.
- 응답 중 도착한 과거 요청은 앱의 세션·목록 세대 번호로 무효화한다. 차단 전 응답이 늦게 도착해 콘텐츠·캐시를 복원하지 않게 한다.

## 7. 공용 Redis 캐시와 개인별 결과

현재 키 `posts:list:limit:*:cursor:*`는 사용자 구분이 없다. 로그인 차단 결과를 여기에 저장하거나 이 캐시에서 먼저 20개를 읽고 필터링하면 안 된다.

초기 구현의 기본 선택:

- 익명 공개 목록만 기존 공용 캐시 경로를 유지한다.
- 로그인한 목록은 공용 완성 페이지 캐시를 우회하고 SQL에서 차단 조건을 포함해 조회한다.
- Redis 전체 삭제·모든 사용자 캐시 삭제로 차단 효과를 구현하지 않는다.
- 본문 수정·삭제의 기존 공용 캐시 무효화는 유지한다. 차단 해제가 공용 원본 데이터를 변경하는 것은 아니다.

개인별 캐시가 실제로 필요해지면 조회자 ID + 차단 변경 버전 + 쿼리/커서를 키에 포함하고, 차단 커밋과 버전 갱신의 원자성·오래된 요청의 캐시 재삽입을 설계한다. userId만 키에 붙이거나 TTL 만료만 기다리는 방식으로 즉시 차단을 보장하지 않는다.
향후 로그인 SQL 부하는 차단 관계 수·인기 글 분포·다른 커서로 측정하고 EXPLAIN (ANALYZE, BUFFERS)로 인덱스 사용을 확인한다.

## 8. 채팅과 차단 경합

- 새 방 생성뿐 아니라 기존 DIRECT 방을 반환하는 경로에도 어느 방향이든 차단 조건을 적용한다.
- 방 목록·마지막 메시지·과거 메시지 조회·socket join·메시지 저장 경로를 같은 정책으로 보호한다. 방에 들어올 때 한 번 검사한 값만 재사용하지 않는다.
- 단순히 차단 조회 후 저장하면 그 사이의 차단과 경합할 수 있다. 필요 시 정렬된 두 사용자 ID에 대한 트랜잭션 advisory lock 등으로 차단/해제와 방 생성·메시지 저장의 공통 직렬화 경계를 만든다.
- 잠금 키·획득 순서는 양방향 모두 동일해야 하며 모든 해당 경로가 같은 규칙을 따른다. 차단 API에만 잠금을 넣고 전송 경로를 빠뜨리지 않는다.
- 기준: 차단 커밋 이후 시작된 전송은 거절. 차단 이전에 이미 커밋된 메시지나 네트워크에 실린 응답을 소급 취소한다고 보장하지 않는다.
- HTTP 차단 성공 후 현재 앱의 방 화면·구독을 정리한다. 이후 차단 전 저장·전송된 이벤트가 도착해도 현재 차단·세션 상태로 화면 반영을 막는다.
- 전역 Socket.IO 연결 전체를 끊어 다른 상대와의 채팅까지 중단시키지 않는다. 필요한 방·구독만 정리한다.
- 양쪽 차단 관계가 모두 없어져야 기존 방을 다시 이용할 수 있다. 한쪽 해제만으로 상대방 차단을 우회하지 않는다.

## 9. 알림·다른 기기의 일관성

- 신규 글 알림 대상 선정 시 수신자가 작성자를 차단했으면 알림 저장·FCM 대상에서 제외한다.
- 큐 대기 중 차단될 수 있으므로 작업 생성 시점 검사만으로 끝내지 않고 실제 처리/전송 직전에 다시 확인한다. FCM에 이미 제출된 알림은 회수할 수 없다.
- 기존 NEW_POST 알림 목록·미읽음 개수도 같은 가시 조건을 적용한다. 현재 알림 data의 authorId를 사용하며 신규 이벤트에서는 서버가 작성자를 결정한다.
- 읽음 처리·전체 읽음·카운트가 숨겨진 알림 때문에 서로 어긋나지 않게 정책과 테스트를 맞춘다. 과거 data에 authorId가 없으면 postId로 작성자를 확인하거나 안전한 별도 처리 방침을 정한다. 무조건 노출하지 않는다.
- 딥링크 클릭 시 서버의 최신 상세 접근 정책을 확인한다. 푸시 수신이 접근 권한의 증거는 아니다.
- 현재 기기는 차단 성공 직후 반영한다. 다른 기기는 앱 재개·명시적 새로고침·재접속 시 최신 차단 설정을 반영한다.
- 기기 간 즉시 갱신까지 필요하면 사용자별 가시성 변경 이벤트와 재조회 계약을 추가한다. 현재 기능에 이미 있다고 가정하지 않는다.
- 비행기 모드의 다른 기기에 즉시 원격 차단을 강제할 수 없다는 한계를 명시한다.

## 10. Flutter 연동과 오프라인 캐시

앱별 구현·파일 위치·검증은 Flutter 저장소 `docs/USER_BLOCKING.md`를 따른다.

현재 PostListModel과 Drift CachedPosts에는 작성자 ID·계정 소유 정보가 없다. 개인별 차단을 확인하지 않은 기존 공개 스냅샷을 로그인 사용자에게 보여주면 차단 글이 다시 나타날 수 있다.

- 서버 DTO의 authorId 추가 → 앱 모델/생성 코드/변환 경로를 함께 정리한다. 닉네임으로 차단 대상을 식별하지 않는다.
- 로그인·로그아웃·계정 변경과 차단·해제 시 목록·검색·상세·댓글·채팅·알림의 영향 범위와 진행 중 응답을 무효화한다.
- 초기 버전은 검증된 개인 가시성 정보가 없는 로그인 목록의 디스크 fallback을 사용하지 않는 보수적 정책으로 시작한다. 익명 캐시를 로그인 뒤 재사용하지 않는다.
- 로그인 오프라인 조회를 유지하려면 계정·작성자 ID·가시성 버전의 스키마·저장 정책과 서버 재검증을 먼저 설계한다. 현재 postId 단일 키 테이블만으로 안전하다고 가정하지 않는다.
- 차단 요청 실패면 성공으로 표시하지 않는다. 결과 미확정이면 결과 조회/수렴 절차를 사용한다. 로그인 상태·차단 사용자 ID의 오래된 스냅샷을 다른 계정에 적용하지 않는다.
- 차단 목록 해제 후 목록을 새로 조회해 비어 있는 페이지와 커서를 정리한다. 차단 필터를 차단 관리 목록에 재적용하지 않는다.
- 다국어·확인 다이얼로그·요청 중 버튼 비활성화·오류·빈 목록·재시도와 테마·반응형을 포함한다.

## 11. 단계별 구현 위치와 완료 기준

소스 코드는 사용자가 한 단계씩 적용한다. 아래는 예정 위치이며 구현 완료 목록이 아니다.

| 단계 | 위치·작업 | 완료 기준 |
| --- | --- | --- |
| 1 | `src/user-blocks/entities/user-block.entity.ts` | 관계·유니크·자기 차단 방지·FK·정밀도 정의 |
| 2 | 추가 마이그레이션·개발/테스트 DataSource | 기존 테이블 변경 없이 생성·검증, 테스트 격리 |
| 3 | user-blocks의 dto/repositories/services | 본인 ID 강제, 반복·동시 요청·탈퇴 경합, 최소 응답 |
| 4 | controllers와 `user-blocks.module.ts` | PUT/DELETE/GET과 인증·ID·커서·limit 검증 |
| 5 | optional guard/decorator, Posts/Comments 모듈·서비스 | 조회자 전달, NOT EXISTS, 정렬·커서·캐시·상세 접근 |
| 6 | 서버 단위·DB/HTTP 통합 테스트 | 서로 다른 사용자·익명·잘못된 인증·연속 페이지와 변경 검증 |
| 7 | Flutter 모델·API·Repository·UseCase·State/Provider | 계정별 수명·진행 중 응답·오프라인 가시성 정책 |
| 8 | 상세/댓글 메뉴·설정 차단 목록·라우터·ARB | 차단·해제·페이지네이션과 빈/실패 상태, 세션 전환 |
| 9 | Chat·Gateway·알림 큐·미읽음 수 | 신규·기존 연결·전송 경합·푸시 대상의 정책 일치 |
| 10 | 종합 회귀와 성능 | 예전 앱/캐시 업그레이드, 실제 앱 동작과 SQL 지표 확인 |

단계 5 이전에는 차단 관계가 저장돼도 콘텐츠 숨김이 완료된 것이 아니다. 단계 9 이전에는 채팅·알림을 포함한 앱 전체 차단이 완료됐다고 보고하지 않는다.

## 12. 필수 검증 시나리오

- A가 B 차단, C 미차단: A에게 B 글/댓글 제외, C와 익명은 정책에 맞는 결과. 다른 계정에 A의 필터가 전파되지 않음.
- 반복·동시 PUT 후 한 관계, blockedAt 유지. 반복 DELETE 204. 자기 차단·삭제된 계정·잘못된 인증·타인 관계 해제 거부.
- 같은 createdAt, 차단 작성자 글이 원본 첫 페이지 전부/중간/끝에 배치된 데이터. 차단 조건 적용 후 limit·정렬·hasNext·nextCursor 정확성.
- 보이는 콘텐츠가 더 있는데 빈 중간 페이지를 반환하거나 마지막 페이지를 잘못 판단하지 않음. 모든 콘텐츠가 차단 대상이면 빈 마지막 페이지.
- 차단/해제 도중 기존 요청 지연, 반환 전 로그아웃·다른 계정 로그인: 늦은 응답이 화면·캐시를 복원하지 않음.
- 익명 캐시를 워밍업한 뒤 A 로그인해도 B 콘텐츠가 공용 캐시에서 반환되지 않음. A 조회가 C·익명 캐시를 덮어쓰지 않음.
- 상세 주소·댓글 API·내 댓글·알림 링크로 차단 콘텐츠를 우회 조회하지 못함.
- 차단 목록 limit+1·동일 blockedAt 정렬·해제 후 첫 페이지·빈 목록·상대 탈퇴 정리 검증.
- 기존 소켓·새 소켓·기존 방 재진입·양쪽 전송과 차단 경합, 양방향 차단 중 한쪽만 해제 검증.
- 알림 전송 큐 대기 중 차단, 저장된 알림 숨김과 미읽음 수 일치. 실제 FCM은 모의 어댑터로 검사.
- 로그인/익명 목록·검색·댓글의 기존 기능 회귀. 관리자 검수 API의 결과·권한은 유지.
- 차단 관계가 많아져도 항목별 N+1 없이 필터 SQL과 인덱스 사용 확인. 비용 목표는 실제 측정 후 정함.

단위/통합 테스트는 기존 운영 데이터·실제 메시지 발송 없이 격리 실행한다. 기존 테스트 개수나 lint/build 통과를 차단 기능 검증으로 대신하지 않는다.
